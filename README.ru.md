# MenuBench

[English](README.md) · **Русский**

Бенчмарк и эталонный конвейер разбора цен в меню ресторанов: фото, сканы, PDF.

> Неверная цена на экране хуже пустой рамки.

Поэтому системам разрешено сказать «не уверен», и это входит в оценку: кроме F1 у каждой конфигурации есть
**кривая risk–coverage** (доля ошибок среди цен, которые система решилась поставить, при каждом уровне покрытия),
ошибка калибровки, а у эталонного конвейера — рабочая точка, замороженная на dev и проверенная на test.

**Статус:** v0.1, заморожено на синтетике (тег `v0.1-frozen`). Следующий шаг — реальные фото меню: разметчик готов,
конвейер заморожен, реальный сплит станет честной отложенной проверкой.

![Risk–coverage на тестовой синтетике](reports/risk_coverage.png)

## Результаты

Тестовая синтетика: **197 меню, 3 792 цены**, 7 раскладок (2 не встречались при разработке), чистый рендер,
сканы и изображения «под фото», ru и en. Все цифры ниже — на test; на нём ничего не подбиралось.

### Что я понял

1. **Один вызов сильной VLM обыгрывает мой многоступенчатый конвейер.** Claude Haiku 5.5 читает всё меню за один
   вызов: 97.2% pair F1 (верная цена *и* верная позиция) за $0.0014 за меню. Мой конвейер на Gemini 2.5 Flash-Lite —
   70.6%; та же дешёвая модель «в лоб» — 90.1%. Конвейер проектировался под слабые модели, которым нужны OCR,
   вырезки и голосование; с текущими моделями лишние стадии в основном добавляют места, где теряются цены.
2. **Порог, откалиброванный на dev, не пережил сдвиг на test.** Конвейер должен был ставить цены без проверки
   с ошибкой ≤1%. На test он поставил 4.8% цен, и 15.3% из них неверны: 8.1% на знакомых раскладках и 17 из 17
   на отложенной раскладке «цена слева» (заголовки разделов уверенно принимались за названия блюд). Ошибка
   калибровки на dev «на тех же данных» — 0.004, на test — 0.069. Селективному предсказанию нужны данные для
   калибровки, похожие на боевые, и детектор «эта раскладка новая».
3. **Голосование работает, но только против независимых ошибок.** Один проход 60.3% → два прохода 65.7% →
   плюс третий при споре 70.6% pair F1. Когда все проходы видят один и тот же обманчивый контекст, они дружно
   соглашаются с одной и той же ошибкой; разные вырезки и сигнал «название ниже цены» исправили этот случай на dev.
4. **Привязка к каталогу без предохранителей ставит на экраны неверные цены.** LLM выбирает позицию каталога
   напрямую: 27.1% привязок неверны (794 неверные цены на экранах). Строгий линкер, доверяющий всем ценам: 13.9%.
   Строгий линкер, который привязывает только цены с откалиброванной уверенностью: 6.1% (10 неверных цен) —
   ценой того, что автоматически привязывается лишь 6.9%. Подсказки держат верную позицию в топ-3 в 99.8% случаев,
   так что работа оператора — один клик.
5. **Самооценка уверенности моделей — от полезной до бесполезной.** Уверенность Claude хорошо ранжирует его же
   ошибки (AURC 0.007; с порогом, подобранным задним числом, можно было бы ставить 89% всех цен при ошибке ≤2%);
   у Qwen3-VL-8B — нет (AURC 0.243).
6. **Текст меню читают все VLM, показать, где он, умеют немногие.** Все кандидаты в OCR распознают 97–99% строк,
   но только Gemini и Qwen3-VL-235B ставят ~90% из них на место. Привязка по одной геометрии — 86% на чистом
   рендере — падает до 31.8%, как только страницы повёрнуты и «сфотографированы».

## Что меряется

- **Трек A — извлечение.** На входе картинка или PDF, на выходе `{цена, валюта, позиция, рамка, уверенность}`.
  Сопоставление один к одному по значению и положению; для pair F1 цена засчитывается только с верным названием
  (после нормализации, CER ≤ 0.15). Зачёркнутая старая цена, выданная как текущая, — ошибка.
- **Трек B — привязка к каталогу с отказом.** Каждая цена привязывается к каталогу в духе кассы (сокращения,
  опечатки, транслит, коды, похожие позиции, позиции, которых нет) — или получает подсказку либо отказ с причиной.
  Главная цифра — неверные привязки: это неверные цены на экранах.
- Селективное предсказание: risk–coverage, AURC, безопасная полнота при риске 1/2/5%, ECE и замороженная рабочая точка.
- Стоимость ($/меню по учёту OpenRouter) и задержка (p50/p95).

## Эталонный конвейер

```
VLM-OCR (тайлы, «родной» формат рамок) → кандидаты-цены (шаблоны, цены внутри строк, защита от телефонов и граммовок)
  → название позиции: вырезка с ценой в красной рамке + соседние строки OCR, 2 прохода, 3-й при споре
  → сигналы (согласие, уверенность модели, геометрия, положение названия, выравнивание в колонку)
  → калибровка (логистическая + изотоническая, только dev) → поставить автоматически или на проверку
  → строгий линкер каталога → LLM-арбитр переупорядочивает подсказки, но не привязывает → привязка | подсказка | отказ
```

## Данные

- **Генератор синтетики** (`menubench synth`): контент ru/en из собственных словарей, 7 HTML-раскладок, рендер
  в headless Chromium, точные рамки каждой строки из DOM; трудные случаи (зачёркнутые цены, «от», диапазоны,
  граммовки, сетки размеров, длинные описания, отвлекающие строки); искажения «скан» и «фото» как гомографии
  плюс свет, блик, размытие, шум и JPEG, рамки проходят то же преобразование; кассовый каталог к каждому меню.
  Две раскладки («цена слева», альбомный ТВ-экран) есть только в test.
- **Реальные фото** собираются после заморозки и размечаются в веб-разметчике; затем замороженный конвейер один раз
  прогоняется на них (`menubench run <config> --dataset data/real --split real-test`).

## Решения и компромиссы

- **Чистая комната.** Никакого кода, промптов и данных работодателя; другие провайдеры, чем в рабочих проектах.
- **VLM в роли OCR, выбор по замерам.** Рамки запрашиваются в «родном» формате модели (`bbox_2d` 0–1000, `box_2d`
  с y впереди), structured output там, где он поддерживается, а сломанный JSON «спасается», а не роняет меню.
- **Распознавание и локализация оцениваются отдельно**, потому что ломаются по-разному.
- **Уверенность обучается, пороги замораживаются.** Калибровка и пороги подбираются только на dev; CLI отказывается
  калибровать на любом другом сплите. Test меряет, что делает замороженный порог, — так и стал виден вывод 2.
- **Арбитр не может привязывать.** LLM может переупорядочить и объяснить подсказки; привязывает только
  детерминированный линкер и только для цен, которым конвейер доверяет.
- **Отложенные раскладки остались отложенными.** Провал на «цена слева» был виден в разметчике до финального
  прогона; его не исправляли, чтобы цифры на test остались честными.
- **Воспроизводимость без публикации ответов моделей.** Каждый ответ кэшируется локально по (модель, версия промпта,
  параметры, хэш картинки); `--mode replay` пересчитывает всё без сети. Кэш не публикуется; `--dry-run` оценивает
  стоимость нового прогона.

## Что не сработало

- Предположение, что конвейер из дешёвых вызовов обыграет один сильный вызов (вывод 1).
- Доверие к калибровке «на тех же данных» (вывод 2).
- Голосование большинством против коррелированных ошибок (вывод 3).
- Привязка по одной геометрии на сфотографированных страницах (вывод 6).
- Qwen3-VL-30B, GPT-5-nano и Mistral Small в роли OCR: текст читают, но рамки ставят на полстроки мимо и хуже.

## Что бы я сделал дальше

- Сильная модель «в лоб» — основной читатель, конвейер с вырезками — независимое второе мнение; их **расхождение**
  становится главным сигналом уверенности.
- Калибровка на данных, похожих на боевые (реальные фото), признаки качества картинки (размытие, перспектива)
  и детектор «раскладка выглядит новой», который отправляет меню на проверку.
- Conformal risk control вместо одного замороженного порога, с отдельным сплитом для калибровки.
- Симметричные вырезки: названия справа от цены тоже бывают.

## Повторить

```bash
uv sync
uv run playwright install chromium
uv run menubench synth --out data/synth -n 300 --seed 42      # тот же сид — тот же датасет
cp .env.example .env                                             # задайте OPENROUTER_API_KEY
uv run menubench run configs/e2e-claude-haiku55.yaml --split test --dry-run
uv run menubench run configs/e2e-claude-haiku55.yaml --split test
uv run menubench calibrate runs/<прогон full-gemini25-flash-lite на dev>
uv run menubench report
```

Все эксперименты за этим README (сравнение OCR, базовые линии, эталонный конвейер на dev и test, абляции, привязка)
стоили около **$9** вызовов моделей.

## Веб-приложение

```bash
cd web && npm ci && npm run build && cd ..
uv run menubench serve          # http://127.0.0.1:8000
```

- **Runs** — таблица лидеров, метрики и risk–coverage прогона, срезы, сравнение до трёх прогонов.
- **Разбор меню** — эталон, предсказания по цвету исхода (верно, не та позиция, старая цена, нет в меню, пропущено),
  строки OCR, решения по каталогу и сырые ответы каждой стадии конвейера.
- **Annotate** — загрузка реальных фото или PDF, предразметка конвейером, правка рамок, названий и связей
  «цена → позиция» (`I` позиция, `P` цена, `Del`, `Ctrl+S`).
- **Try it** — загрузите меню и смотрите, как конвейер работает шаг за шагом (server-sent events), или откройте
  готовый пример. Лимиты на IP и суточный бюджет; загрузки удаляются через 24 часа.

Публичный образ (`Dockerfile`) отдаёт только *Try it*; задайте `OPENROUTER_API_KEY`, галерея работает и без него.
