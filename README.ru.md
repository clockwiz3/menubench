# MenuBench

[English](README.md) · **Русский**

Бенчмарк и эталонный конвейер разбора цен в меню ресторанов (фото, сканы, PDF) и привязки их к кассовому каталогу,
построенные на одном правиле: **неверная цена на экране хуже пустой рамки.**

**Результат:** если дать LLM привязывать позиции меню к каталогу напрямую, **27.1%** привязок указывают не на ту
позицию. Когда меню читает сильная модель, независимый конвейер её проверяет, уверенность откалибрована, а линкер
строгий, неверных привязок становится **1.1%**, и **64%** всех цен попадают на экраны без проверки при **1.0%**
ошибок — с порогом, выбранным на dev и только потом измеренным на test. Всё остальное уходит человеку с подсказкой,
в топ-3 которой верная позиция каталога в 100% случаев.

| approach | pair F1 % | auto-placed % | wrong among auto-placed % | wrong catalog links % | $/menu |
|---|---|---|---|---|---|
| Claude reads, pipeline checks, calibrated (v0.2) | 97.2 | 64.0 | 1.0 | 1.1 | 0.0052 |
| Claude Haiku 5.5, one call | 97.2 | – | – | – | 0.0014 |
| reference pipeline, calibrated (v0.1) | 70.6 | 4.8 | 15.3 | 6.1 | 0.0041 |
| reference pipeline + LLM picks the catalog item | 70.6 | 4.8 | 15.3 | 27.1 | 0.0042 |

Тестовая синтетика: 197 меню, 3 792 цены, 7 раскладок (2 не встречались при разработке), чистый рендер, сканы и
изображения «под фото», ru и en. **Pair F1** засчитывает цену, только если верны и значение, и позиция, к которой
она относится: F1 по одним ценам прячет самую частую реальную ошибку — верное число под чужим блюдом.
*Auto-placed* — доля всех цен меню, поставленных без проверки и верных; *wrong among auto-placed* — доля ошибок среди
поставленных. Прочерк значит, что у подхода нет рабочей точки (порога).

![Risk–coverage на тестовой синтетике](reports/risk_coverage.png)

**Статус:** v0.2. Конвейер заморожен до сбора реальных фото; разметчик готов, реальный сплит станет честной
отложенной проверкой. v0.2 проектировалась уже после того, как были известны результаты v0.1 на test (см. ниже),
поэтому реальные фото — чистая проверка и для неё.

## Как я к этому пришёл

**v0.1 — конвейер из дешёвых вызовов.** VLM-OCR, поиск цен, вырезка на каждую цену с красной рамкой, два голоса и
третий при споре, калиброванная уверенность, строгая привязка. На test — 70.6% pair F1; замороженный порог поставил
4.8% цен, и **15.3% из них неверны** при цели 1%. Порог с dev не пережил сдвиг на test: больше изображений «под фото»
и две незнакомые раскладки (на «цене слева» заголовки разделов уверенно принимались за названия блюд, 17 из 17
поставленных цен неверны). При этом один вызов Claude Haiku 5.5 читал те же меню с 97.2% pair F1 за $0.0014.

**v0.2 — сильная модель читает, конвейер проверяет.** Один вызов точен, но не знает, где ошибается. Конвейер v0.1
слабее, но ошибается по-другому, поэтому его согласие с читателем — сигнал. Откалиброванная только на dev общая
уверенность дала рабочую точку 1%, которая удержалась на test (64.0% поставлено, 1.0% ошибок).

| calibrated on | AURC ↓ | best possible auto-placed at ≤1% (hindsight) % | auto-placed at the dev threshold % | wrong among them % |
|---|---|---|---|---|
| reader confidence + verifier agreement | 0.0104 | 60.3 | 64.0 | 1.0 |
| reader confidence only | 0.0075 | 26.3 | 0.0 | – (n=0) |

Собственная уверенность читателя ранжирует ошибки на test не хуже (AURC 0.0075 против 0.0104), но на dev она ни при
каком пороге не опускалась ниже 1% ошибок, так что выбрать по ней рабочую точку было нельзя. Именно согласие
верификатора сделало возможным порог 1%, выбранный на dev, и этот порог перенёсся. Какой сигнал лучше выдержит
реальные фото — открытый вопрос.

## Что я понял

1. **Что попадает на экран, решают предохранители, а не выбор модели.** Прямая привязка через LLM: 27.1% неверных
   привязок. Строгий линкер, доверяющий всем ценам: 13.9%. Строгий линкер только для цен, которым доверяют оба мнения: 1.1%.
2. **Конвейер из дешёвых вызовов проиграл одному сильному вызову.** v0.1 — 70.6% pair F1 против 97.2%; даже та же
   дешёвая модель «в лоб» — 90.1%. Лишние стадии чаще теряли цены, чем добавляли точность.
3. **Калибровка «на тех же данных» — не доказательство.** Ошибка калибровки v0.1 — 0.004 на dev и 0.069 на test, порог
   сломался при сдвиге. Теперь пороги выбираются на dev и только измеряются на test; CLI отказывается калибровать на
   любом другом сплите.
4. **Расхождение двух по-разному устроенных систем — лучший сигнал, чем уверенность любой из них**, если нужен порог,
   которому можно доверять.
5. **Голосование помогает только против независимых ошибок.** Один проход 60.3% → два 65.7% → плюс третий при споре
   70.6%; если все проходы видят один и тот же обманчивый контекст, они дружно соглашаются с ошибкой.
6. **Текст меню читают все VLM, показать, где он, умеют немногие.** Все кандидаты в OCR распознают 97–99% строк, но
   только Gemini и Qwen3-VL-235B ставят ~90% из них на место. Привязка по одной геометрии (86% на чистом рендере)
   падает до 31.8% на повёрнутых и «сфотографированных» страницах.

Для сравнений: меню здесь синтетические и намеренно трудные — перспектива, блики, размытие, незнакомые раскладки, —
чтобы найти, где системы ломаются. С цифрами на однотипных боевых меню известного формата их сравнивать нельзя.

## Что меряется

- **Трек A — извлечение.** На входе картинка или PDF, на выходе `{цена, валюта, позиция, рамка, уверенность}`.
  Сопоставление один к одному по значению и положению; для pair F1 цена засчитывается только с верным названием
  (после нормализации, CER ≤ 0.15). Зачёркнутая старая цена, выданная как текущая, — ошибка.
- **Трек B — привязка к каталогу с отказом.** Каждая цена привязывается к каталогу в духе кассы (сокращения,
  опечатки, транслит, коды, похожие позиции, позиции, которых нет) — или получает подсказку либо отказ с причиной.
  Главная цифра — неверные привязки: это неверные цены на экранах.
- Селективное предсказание: risk–coverage, AURC, безопасная полнота при риске 1/2/5%, ECE и замороженная рабочая точка.
- Стоимость ($/меню по учёту OpenRouter) и задержка (p50/p95).

## Конвейеры

v0.1, верификатор:

```
VLM-OCR (тайлы, «родной» формат рамок) → кандидаты-цены (шаблоны, цены внутри строк, защита от телефонов и граммовок)
  → название позиции: вырезка с ценой в красной рамке + соседние строки OCR, 2 прохода, 3-й при споре
  → сигналы (согласие, уверенность модели, геометрия, положение названия, выравнивание в колонку)
  → калибровка (логистическая + изотоническая, только dev) → поставить автоматически или на проверку
  → строгий линкер каталога → LLM-арбитр переупорядочивает подсказки, но не привязывает → привязка | подсказка | отказ
```

v0.2, второе мнение: Claude Haiku 5.5 читает всё меню одним вызовом; v0.1 независимо работает на той же картинке;
для каждой цены — нашёл ли верификатор ту же цену и ту же позицию, насколько уверен каждый → калиброванная
уверенность → поставить или на проверку → строгая привязка только для цен, которым доверяют.

## Данные

- **Генератор синтетики** (`menubench synth`): контент ru/en из собственных словарей, 7 HTML-раскладок, рендер
  в headless Chromium, точные рамки каждой строки из DOM; трудные случаи (зачёркнутые цены, «от», диапазоны,
  граммовки, сетки размеров, длинные описания, отвлекающие строки); искажения «скан» и «фото» как гомографии
  плюс свет, блик, размытие, шум и JPEG, рамки проходят то же преобразование; кассовый каталог к каждому меню.
  Две раскладки («цена слева», альбомный ТВ-экран) есть только в test.
- **Реальные фото** собираются после заморозки и размечаются в веб-разметчике; затем замороженный конвейер один раз
  прогоняется на них (`menubench run <config> --dataset data/real --split real-test`).

## Решения и компромиссы

- **Чистая комната.** Никакого кода, промптов и данных работодателя; другие провайдеры, чем в рабочих проектах.
- **VLM в роли OCR, выбор по замерам.** Рамки запрашиваются в «родном» формате модели (`bbox_2d` 0–1000, `box_2d`
  с y впереди), structured output там, где он поддерживается, а сломанный JSON «спасается», а не роняет меню.
- **Распознавание и локализация оцениваются отдельно**, потому что ломаются по-разному.
- **Уверенность обучается, пороги замораживаются.** Калибровка и пороги подбираются только на dev; CLI отказывается
  калибровать на любом другом сплите. Test меряет, что делает замороженный порог, — так и стал виден вывод 2.
- **Арбитр не может привязывать.** LLM может переупорядочить и объяснить подсказки; привязывает только
  детерминированный линкер и только для цен, которым конвейер доверяет.
- **Отложенные раскладки остались отложенными.** Провал на «цена слева» был виден в разметчике до финального
  прогона; его не исправляли, чтобы цифры на test остались честными.
- **Воспроизводимость без публикации ответов моделей.** Каждый ответ кэшируется локально по (модель, версия промпта,
  параметры, хэш картинки); `--mode replay` пересчитывает всё без сети. Кэш не публикуется; `--dry-run` оценивает
  стоимость нового прогона.

## Что не сработало

- Предположение, что конвейер из дешёвых вызовов обыграет один сильный вызов (вывод 2).
- Доверие к калибровке «на тех же данных» (вывод 3).
- Голосование большинством против коррелированных ошибок (вывод 5).
- Привязка по одной геометрии на сфотографированных страницах (вывод 6).
- Qwen3-VL-30B, GPT-5-nano и Mistral Small в роли OCR: текст читают, но рамки ставят на полстроки мимо и хуже.

## Что бы я сделал дальше

- Реальные фото: перепроверить рабочую точку v0.2 и сравнить сигнал верификатора с собственной уверенностью читателя.
- Верификатор подешевле: всего конвейера v0.1 для второго мнения слишком много.
- Калибровка на данных, похожих на боевые (реальные фото), признаки качества картинки (размытие, перспектива)
  и детектор «раскладка выглядит новой», который отправляет меню на проверку.
- Conformal risk control вместо одного замороженного порога, с отдельным сплитом для калибровки.
- Симметричные вырезки: названия справа от цены тоже бывают.

## Повторить

```bash
uv sync
uv run playwright install chromium
uv run menubench synth --out data/synth -n 300 --seed 42      # тот же сид — тот же датасет
cp .env.example .env                                             # задайте OPENROUTER_API_KEY
uv run menubench run configs/e2e-claude-haiku55.yaml --split test --dry-run
uv run menubench run configs/e2e-claude-haiku55.yaml --split test
uv run menubench run configs/second-opinion-claude.yaml                  # прогон на dev для калибровки
uv run menubench calibrate runs/<этот прогон> --out configs/calibration/second-opinion-claude.json
uv run menubench run configs/second-opinion-claude-cal.yaml --split test
uv run menubench report
```

Все эксперименты за этим README (сравнение OCR, базовые линии, оба конвейера на dev и test, абляции, привязка)
стоили около **$10** вызовов моделей.

## Веб-приложение

```bash
cd web && npm ci && npm run build && cd ..
uv run menubench serve          # http://127.0.0.1:8000
```

- **Runs** — таблица лидеров, метрики и risk–coverage прогона, срезы, сравнение до трёх прогонов.
- **Разбор меню** — эталон, предсказания по цвету исхода (верно, не та позиция, старая цена, нет в меню, пропущено),
  строки OCR, решения по каталогу и сырые ответы каждой стадии конвейера.
- **Annotate** — загрузка реальных фото или PDF, предразметка конвейером, правка рамок, названий и связей
  «цена → позиция» (`I` позиция, `P` цена, `Del`, `Ctrl+S`).
- **Try it** — загрузите меню и смотрите, как конвейер работает шаг за шагом (server-sent events), или откройте
  готовый пример. Лимиты на IP и суточный бюджет; загрузки удаляются через 24 часа.

Публичный образ (`Dockerfile`) отдаёт только *Try it*; задайте `OPENROUTER_API_KEY`, галерея работает и без него.
