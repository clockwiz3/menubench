# MenuBench — план реализации

> Открытый бенчмарк и эталонный конвейер разбора цен в меню (фото, сканы, PDF).
> Главная идея: **неверная цена на экране хуже пустой рамки**, поэтому система умеет отказываться
> от ответа, а качество меряется не одной точностью, а кривой «покрытие против точности».

## Принятые решения

| Вопрос | Решение |
|---|---|
| Имя | `menubench` |
| README | два языка: `README.md` (en) и `README.ru.md` (ru), ссылки друг на друга в шапке |
| Кэш ответов моделей | **не публикуется**: локальный, в `.gitignore`. Наружу идут только метрики и отчёты |
| OCR | модель с OpenRouter (VLM в роли OCR), выбираем замерами; локальный OCR не нужен |
| Данные | сначала только синтетика; реальные фото добавляются позже, когда конвейер готов и заморожен |
| Веб-интерфейс | FastAPI + Vue 3: просмотр прогонов, разметчик реальных фото, публичное демо — одно приложение |

## 0. Чистая комната (прочитать до первой строки кода)

Проект — переосмысление опыта, а не перенос рабочего кода.

- Ни строки кода, промптов, схем БД и данных из репозиториев работодателя (`smp-client`, `decker-*` и т.п.).
- Другие провайдеры, чем на работе (OCR — VLM с OpenRouter, а не Yandex Vision), свои промпты, свои данные.
- В README нет названий клиентов и внутренних цифр — только цифры, полученные на этом бенчмарке.

## 1. Цель и критерии готовности

**Для кого:** нанимающий инженер, который за 2 минуты в README должен увидеть evals, компромиссы и инженерную зрелость.

Проект готов, когда:

1. Генератор синтетики воспроизводимо (по сиду) выдаёт ≥ 300 меню с точной разметкой; есть ≥ 100 реальных фото с ручной разметкой.
2. `uv run menubench eval` пересчитывает все таблицы README; с локальным кэшем — без сети и бесплатно.
3. Таблица лидеров: ≥ 5 конфигураций (модели × стратегии) по качеству, цене и задержке.
4. Есть кривая coverage/accuracy и выбранная рабочая точка с обоснованием.
5. **Разрыв синтетика → реальность** измерен и объяснён: конвейер заморожен до сбора фото, поэтому реальный сплит — честный held-out.
6. Живое демо: загрузил меню — по шагам видно, как идёт конвейер, затем цены, позиции и что система
   отказалась размечать и почему.
7. Разделы «Решения и компромиссы» и «Что не сработало» — в обоих README.

## 2. Постановка задачи

### Трек A — извлечение
Вход: изображение или PDF меню. Выход: список `{price, currency, name, bbox_price, bbox_name?, confidence}`.

### Трек B — привязка к каталогу с отказом
Вход: меню + каталог позиций заведения (список названий, как в кассе: сокращения, опечатки, другой порядок слов).
Выход по каждой цене: `link(catalog_id)` | `hint([кандидаты], причина)` | `abstain(причина)`.

Трек B отличает проект от «очередного OCR-демо»: каталог моделирует реальный POS,
а метрика штрафует уверенную ошибку сильнее, чем отказ.

## 3. Данные

### 3.1 Синтетика (основной источник на этапе разработки)

Генератор: **контент → HTML-шаблон → рендер в Playwright → аугментации «под фото»**.
Разметка получается бесплатно и точно: bbox каждой цены и названия берётся из DOM (`getBoundingClientRect`)
и пересчитывается через те же геометрические преобразования, что и картинка.

- **Контент:** блюда, разделы и цены из словарей ru/en (комбинаторика: основа + способ приготовления + гарнир),
  ценовые сетки по типу заведения (кофейня, бургерная, ресторан, столовая). Без вызовов LLM — детерминированно по сиду.
- **Шаблоны раскладок (8–10):** две колонки; таблица с точками-заполнителями; цена под названием;
  цена слева; варианты размеров S/M/L в столбцах; сетка карточек с картинками-заглушками; «меловая доска»
  с рукописным шрифтом; узкий лист-стойка; PDF на несколько страниц.
- **Трудные случаи (подмешиваются с заданной частотой):** граммовки `250 г`, калории, телефон и адрес,
  даты, зачёркнутая старая цена, `от 300`, диапазоны `300–450`, валюты `₽ $ € ₸`, форматы `3.50`, `350,-`, `350 р.`,
  цена без валюты, позиция с описанием в 2–3 строки, одна цена на несколько позиций.
- **Аугментации (уровни `clean` / `scan` / `photo`):** перспектива, поворот, размытие, шум, JPEG-артефакты,
  неравномерный свет и блик, тень, низкое разрешение. Уровень записывается в метаданные — по нему режутся отчёты.
- **Каталог для трека B:** генерируется из того же контента — сокращения, транслит, опечатки, перестановки слов,
  дистракторы (похожие, но не те позиции); часть позиций меню в каталоге отсутствует (правильный ответ — отказ).
- **Воспроизводимость:** датасет = версия генератора + сид. Картинки в git не кладём, `menubench synth --seed 42 -n 300`
  собирает их локально. Опубликовать готовый архив синтетики на HF можно позже — это не кэш, решим отдельно.

### 3.2 Реальные фото (позже)

- Свои фото меню кафе и ресторанов; перед публикацией убрать лица и персональные данные.
- Разметка: предразметка уже готовым конвейером → правка руками в веб-разметчике (раздел 7, делается заранее, в M9).
- 20% фото размечаются повторно через неделю, считается согласие разметки.

### 3.3 Сплиты
- `synth-dev` — подбор промптов и порогов.
- `synth-test` — финальные замеры на синтетике, пороги на нём не подбираются.
- `real-test` — только финальный прогон замороженного конвейера. Калибровку под реальные фото, если понадобится,
  делаем на отдельном `real-dev` и честно показываем обе цифры: до и после.

## 4. Метрики

| Метрика | Что меряет |
|---|---|
| OCR line recall / CER | насколько VLM-OCR вообще видит текст (по синтетике известен эталон каждой строки) |
| bbox IoU | насколько точны координаты от VLM — у VLM это слабое место, меряем отдельно |
| Price P/R/F1 | нашли ли цены (значение + IoU bbox ≥ 0.5) |
| Name accuracy | верно ли названа позиция у цены (нормализация + порог по CER, отдельно exact) |
| Pair F1 | пара «цена-название» целиком верна |
| **Selective risk @ coverage** | доля ошибок среди того, что система решилась разметить |
| **AURC** | площадь под кривой risk–coverage, одно число для сравнения стратегий |
| Wrong-link rate (трек B) | доля уверенных неверных привязок — главная «опасная» метрика |
| Hint usefulness (трек B) | в скольких подсказках правильный кандидат в top-3 |
| $/menu, p50/p95 latency | стоимость и задержка на меню |

Отчёт по срезам: шаблон, уровень аугментации, язык, тип трудного случая; отдельно synth против real.

## 5. Конвейер

```
ingest ──► ocr ──► price_detect ──► name_attribution ──► vote/aggregate ──► link ──► arbiter ──► decide
 PDF→PNG   VLM:     регэксп+          VLM на кропе с      2 прохода, 3-й     строгая   LLM: топ-k     link | hint
 нормализ. строки   геометрия         контекстом           при споре          норм. +   кандидатов    | abstain
           +bbox    (колонки,                                                 fuzzy     + объяснение
                    выравнивание)
```

- **ingest:** PDF через pypdfium2, EXIF-поворот, даунскейл до бюджета токенов модели.
- **ocr:** интерфейс `OcrEngine.run(image) -> list[Line]`. Реализация — VLM с OpenRouter: строки текста + bbox в JSON.
  - Координаты у моделей в разных системах (пиксели, 0–1, 0–1000) — нормализатор по семейству модели в конфиге.
  - Проверка bbox: сверка с нарезкой (кроп по bbox → текст должен совпасть), сомнительные строки помечаются.
  - Большие меню режутся на тайлы с перекрытием, строки на стыках склеиваются.
  - Кандидаты для замеров — несколько VLM разных размеров и цен; выбор по OCR recall, IoU и $/страницу.
- **price_detect:** регэкспы форматов и валют + отсев граммовок, калорий, телефонов по контексту + геометрия
  (кластеризация по колонкам, выравнивание по правому краю, линии из точек).
- **name_attribution:** VLM получает кроп вокруг цены (строка + соседи) и весь кадр в низком разрешении,
  отвечает JSON по схеме. Два независимых прохода (разная температура / разный кроп), при расхождении — третий,
  решает большинство. Согласие проходов — один из сигналов уверенности.
- **aggregate:** уверенность = f(согласие проходов, уверенность OCR, геометрическая однозначность).
  Калибровка на `synth-dev` (isotonic / Platt), чтобы confidence 0.9 значил ~90%.
- **link:** нормализация (регистр, ё/е, транслит, единицы), строгое совпадение → fuzzy (rapidfuzz) с порогом.
  Два близких кандидата — не привязка, а подсказка.
- **arbiter:** LLM получает цену, название, top-k кандидатов и **не решает**, а ранжирует и объясняет.
- **decide:** порог по калиброванной уверенности; всё ниже — `hint` или `abstain` с человекочитаемой причиной.

### Базовые линии (без них таблица ничего не значит)
1. **VLM end-to-end:** одна картинка → один вызов → JSON всех цен. Решение «в лоб».
2. **VLM-OCR + эвристики:** OCR-стадия той же моделью, дальше без LLM — ближайшая строка слева/сверху от цены.
3. **Полный конвейер** с голосованием и отказом.
4. Абляции: без 3-го прохода, без геометрии, без калибровки, без арбитра.

### Модели
Всё через OpenRouter (с запасным провайдером в настройках маршрутизации): Qwen-VL нескольких размеров,
Gemini Flash, Claude Haiku/Sonnet, GPT-класс mini, Mistral. Конкретные ID — в `configs/models.yaml`,
список пересматривается при каждом крупном прогоне (дата фиксируется в отчёте).

## 6. Воспроизводимость и кэш

- Каждый вызов модели кэшируется по ключу `sha256(model, provider, prompt_version, params, image_sha)` в локальной SQLite.
- Кэш **не публикуется** (`.cache/` в `.gitignore`).
- Режимы: `live` (вызов + запись), `replay` (только кэш, промах — ошибка), `record-missing` (по умолчанию).
- Промпты версионируются файлами (`prompts/ocr.v1.md`), версия входит в ключ кэша.
- Каждый прогон пишет `runs/<timestamp>-<config>/`: конфиг, метрики JSON, стоимость, версия генератора, git sha.
  В репозиторий коммитятся только итоговые `reports/` (таблицы и графики для README).
- Для внешнего читателя: `menubench run --dry-run` оценивает стоимость прогона, `--limit N` гоняет сабсет за центы.
- CI: тесты на ручных фикстурах с замоканными ответами моделей — без ключей и сети.

## 7. Веб-приложение

Одно приложение, три раздела. Ядро (`menubench`) от веба не зависит: CLI и API вызывают одни и те же функции.

| Раздел | Для кого | Что делает |
|---|---|---|
| **Runs** — просмотр прогонов | я при отладке, нанимающий инженер | таблица лидеров с фильтрами по срезам; кривые risk–coverage нескольких конфигураций на одном графике; разбор меню: картинка с рамками эталона и предсказания, ошибки подсвечены, рядом сырые ответы моделей по стадиям |
| **Annotate** — разметчик | я, для реальных фото | загрузка фото → предразметка конвейером → правка рамок (перетаскивание, ресайз, новая рамка), названий, типов цен и связей «цена → позиция»; горячие клавиши; сохранение в JSON по `schema.py`; статус «размечено / проверено» |
| **Try** — демо | все | загрузка меню или выбор из галереи примеров; стадии конвейера в реальном времени (SSE); итог: рамки цветом решения (привязка / подсказка / отказ), таблица с уверенностью и причиной, $ и время |

**Бэкенд:** FastAPI, Pydantic-схемы из ядра прямо в ответах API, SQLAlchemy 2 + SQLite (задачи, разметка,
индекс прогонов), задачи конвейера — фоновые asyncio-задачи в процессе с прогрессом по SSE (Redis и Celery
не нужны при одном пользователе-демо; интерфейс очереди оставляем заменяемым).

**Фронтенд:** Vue 3 + TypeScript + Vite, Vue Router, Pinia, Tailwind CSS v4. Рамки и редактор — Konva
(`vue-konva`), графики — ECharts. Типы API генерируются из OpenAPI FastAPI (`openapi-typescript`),
вручную их не пишем; рассинхрон ловит CI.

**Демо наружу:** один Docker-образ (FastAPI отдаёт собранный SPA), хостинг — HF Spaces (Docker) или любой VPS.
Защита бюджета: дешёвая модель по умолчанию, лимит загрузок на IP и суточный потолок в $, размер файла ≤ 10 МБ,
загруженные файлы удаляются через 24 часа, галерея примеров отдаётся из заранее посчитанных результатов.

## 8. Структура репозитория

```
menubench/
  pyproject.toml            # uv, ruff, mypy, pytest
  README.md / README.ru.md
  Dockerfile                # сборка web + запуск API, для демо
  src/menubench/
    schema.py               # Pydantic-модели разметки и предсказаний

    link/                   # нормализация, fuzzy, арбитр, decide
    eval/                   # метрики, матчинг, risk-coverage, отчёты по срезам
    server/                 # FastAPI: роуты runs / annotate / try, задачи, хранилище, лимиты
    cli.py                  # typer: synth / run / eval / report / serve
  web/                      # Vue 3 + Vite
    src/pages/              # RunsPage, MenuReviewPage, AnnotatePage, TryPage
    src/components/         # BBoxCanvas (просмотр), BBoxEditor (правка), RiskCoverageChart, StageTimeline…
    src/api/                # сгенерированные типы + тонкий клиент
  src/menubench/prompts/    # версионированные промпты (*.vN.md)
  configs/                  # YAML конфигураций прогонов и models.yaml
  reports/                  # сгенерированные таблицы и графики для README
  tests/                    # pytest: ядро и API (httpx TestClient)
```

## 12. Риски

| Риск | Что делаем |
|---|---|
| VLM неточно отдаёт bbox | меряем IoU отдельно; тайлинг; проверка кропом; цена матчится по значению + положению с допуском |
| Синтетика слишком «чистая», разрыв с реальностью | аугментации `photo`, разнообразие шаблонов, разрыв меряем и показываем как результат, а не прячем |
| Подгонка под свой генератор | `synth-test` на отдельных сидах и шаблонах, часть шаблонов вообще не видна на dev |
| Провайдер меняет модель под тем же именем | дата и провайдер в кэше и отчёте |
| Проект расползается | трек B и демо — только после рабочей таблицы трека A |
| Веб съедает время конвейера | веб-этапы строго после соответствующего этапа ядра; Runs нужен для отладки, Try — последним |
| Демо сжигают ботами | лимиты на IP, потолок в $, без ключа в браузере — все вызовы только с сервера |
| Загруженные фото с людьми / персональными данными | не храним дольше 24 часов, не используем для датасета без явной галочки |

## 13. Что пойдёт в резюме (черновик)

> **MenuBench** — open-source benchmark and pipeline for menu price extraction with selective prediction.
